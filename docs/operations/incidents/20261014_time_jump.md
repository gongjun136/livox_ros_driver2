2026-10-14，北京时间。`sany-03-master` 实际工作区 `/home/nvidia/gj_ws/lightning_lm_ws`，ROS Humble、域 42，驱动源码 `fbf39f9`。前 192.168.3.184、左 192.168.1.108、右 192.168.2.133 均可发现和响应控制命令，驱动日志包含初始化成功、切换 Normal 成功及启用 IMU 成功；实际没有点云与 IMU 发布。心跳、诊断仍可订阅，不能解释为整个 ROS 图不可发现。

# 原始证据

点云目标为各自 `192.168.N.100:56301`，IMU 为 `:56401`，与主机监听一致。设备只读查询 `cur_work_state=4`（SDK Error），三台 HMS 均含 `0x04050002`（时间同步异常 Warning）。前雷达网卡 3 秒约 3.6 KB，只能辅助说明缺少正常流量，不能代替 UDP 类型抓包。

系统 journal 的同一启动记录：

```text
[  232.034678] chronyd[1421]: System clock wrong by 1791969621.444499 seconds
[  232.035301] chronyd[1421]: System clock was stepped by 1791969621.444499 seconds
[  232.985301] phc2sys[1388]: [232.985] eth1 sys offset -1791969621444499371 s1 freq +62499999 delay 2272
```

用户从同一 journal 打印的墙上时钟记录：

```text
1970-01-01T08:04:54.022935+0800 ubuntuM chronyd[1421]: System clock wrong by 1791969621.444499 seconds
2026-10-14T17:25:15.467752+0800 ubuntuM chronyd[1421]: System clock was stepped by 1791969621.444499 seconds
```

跳变发生在 17:25，而非晚上重新启动驱动时。PTP 早已开始对外授时；三个服务仅 `After=network.target`，Chrony 为 `makestep 1.0 -1`，RTC 为本地时间。晚上检查时 Chrony 与三路 PHC 已稳定，但设备仍无数据。开机为何落到 1970 年、17:25 至晚间设备的完整状态变化未连续采集，不将 RTC 时区配置直接等同于唯一根因。

复查命令（若已重启，用 `journalctl --list-boots` 找到对应启动 ID 替换 `-b`）：

```bash
journalctl -b --no-pager -o short-monotonic -u chrony \
  | grep -E 'Selected source|clock wrong|stepped'
TZ=Asia/Shanghai journalctl -b --no-pager -o short-iso-precise -u chrony \
  | grep -E 'clock wrong|stepped'
journalctl -b --no-pager -o short-monotonic -u ptp_master_eth1_sys \
  | grep -E '\[ *23[0-9]\.'
```

# 结论与修复状态

已证实：开机时间未正确建立就对外 PTP 授时，之后发生巨大跳变；设备在晚间仍停留异常状态，主机驱动重启无效，而设备软重启可逐台恢复。时间同步异常是最有证据支持的解释；没有完整采集链证明 17:25 到恢复之间不存在其他触发因素。

本次补充 @ref livox_time_sync 的启动门槛、PHC 初始化、运行期禁止自动跳时、可回退安装工具及离线回归测试。恢复出数与预防配置部署分别验收：源码完成不等于 root 配置已安装，也不等于整车冷启动验收。管理员安装结果与测试记录必须按实际补充；不自动重启域控或驾驶任务。
